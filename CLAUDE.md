# CLAUDE.md

Go client library for the BeyondTrust Password Safe / Secrets Safe public API
(`github.com/BeyondTrust/go-client-library-passwordsafe`). Library code lives in `api/`, one package per
API area (`secrets`, `managed_account`, `authentication`, `utils`, `entities`, `constants`, ...).
`fuzzing/` holds fuzz targets. `TestClient.go` at the repo root is a manual example, not part of the library.

## Checks (run what CI runs)

- Go version comes from `go.mod` (CI uses `go-version-file: go.mod`).
- Build: `go build ./...`
- Unit tests: `go test -race ./...` (CI runs them from `api/`). Tests read `PASSWORD_SAFE_FAKE_*` fixture
  variables from the `unit_test` GitHub environment; without them, tests in `utils`, `secrets` and
  `managed_account` fail. `gh variable list --env unit_test` shows their values; export them before running
  the tests locally.
- Lint: `golangci-lint` v2.11.4 with `.golangci.yml`. Build it with the `go.mod` toolchain
  (e.g. `GOTOOLCHAIN=go1.26.9 go install github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.11.4`);
  a binary built with a newer Go fails with a typecheck error.
- Cognitive complexity: `gocognit -ignore "_test|testdata" -over 10 .` — functions above 10 fail CI.
  Extract helpers instead of adding branches to long flows such as `CreateSecretFlow`.
- Error strings: lowercase, no trailing punctuation (staticcheck ST1005).

## Commits, PRs and releases

- PR titles must be conventional commits (`feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert`);
  include the Jira key, e.g. `feat: add ... BIPS-12345`.
- CHANGELOG, `version.txt` and tags are generated by release-please. Do not edit them by hand.

## API conventions

- The API version is sent as the `version` query parameter (default 3.0 on the server). Supported values
  are `constants.ApiVersion31` .. `ApiVersion33` plus `"3.0"`.
- Secrets Safe payloads are versioned structs (`SecretCredentialDetailsConfig30` .. `Config33`, text and
  file `Config30` .. `Config32`). `CreateSecretFlow` accepts version-neutral inputs (`SecretCredentialInput`,
  `SecretTextInput`, `SecretFileInput`) and builds the matching struct; versioned structs passed directly
  are sent as is. v3.3 text and file reuse the v3.2 structs.
- Owners: v3.0 uses `OwnerType` + `OwnerId` / `OwnersByOwnerId`; v3.1+ uses `Owners` where each entry has
  `UserId` **or** `GroupId`, not both (sending both returns "Duplicate values in Owners").
  Owner entries are not validated locally (no `dive` tag).
- TOTP is only for credential secrets and only with API v3.3: `TotpEnabled` / `TotpSecretKey` with another
  version are rejected before any request. `TotpSecretKey` is write-only and never logged; TOTP codes
  must never be logged either.
- Updates (`UpdateCredentialSecret`, `UpdateTextSecret`, `UpdateFileSecret`) are PUTs that replace the
  secret: `FolderId`, `Title` and `Owners` are required (the server requires `FolderId` even though the API
  spec marks it read-only), and unsent `Description`, `Notes` and `Urls` are cleared. Credential and text
  updates may answer 204 or 200; file secrets use multipart (`secretmetadata` + `file`) and answer 204.
- Prefer typed sentinel errors checked with `errors.Is` for documented status codes (see
  `secrets.ErrSecretNotCredential`, `secrets.ErrSecretTotpNotAvailable`).
- Validate inputs (IDs, payloads) before making requests, and cover that with tests asserting no request
  was sent.

## Tests

- Use `httptest` servers; helpers such as `newTotpTestSecretObj(t, version, handler)` in
  `api/secrets/secrets_test.go` build a `SecretObj` for a given API version.
- When adding API-version behaviour, test each version shape (3.0, 3.1, 3.2, 3.3).
